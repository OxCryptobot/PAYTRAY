# PayTray Secure Release-Key and Reviewer Sign-Off Templates

**Purpose:** Provide an exact, fail-closed procedure for configuring an Ed25519 release signing key and collecting the four mandatory human approvals for PayTray. These templates contain placeholders only. They do not create approval evidence or contain a real private key.

## 1. Security rules

The private key must be generated by the authorized release operator, stored in an approved secret manager or protected operator environment, and never pasted into chat, committed to Git, placed in a report, or printed to a terminal. The agent must not generate or invent the key on behalf of the approver. The first PayTray release remains Base Sepolia-only unless a separate, explicit mainnet approval is completed.

The signing key proves possession of an operator key; it does **not** replace human approval. The release payload must remain blocked unless the approval artifact, Railway evidence, migration evidence, recovery evidence, manifest, and signing key are all valid.

## 2. Local operator key-generation commands

Run these commands on the authorized operator workstation or a protected release runner, not in a shared repository directory:

```bash
set -eu
umask 077

export PAYTRAY_KEY_DIR="${PAYTRAY_KEY_DIR:-$HOME/.config/paytray/release}"
install -d -m 700 "$PAYTRAY_KEY_DIR"

# Generate a new Ed25519 private key. Do not print the file.
openssl genpkey \
  -algorithm Ed25519 \
  -out "$PAYTRAY_KEY_DIR/release-signing-key.pem"

chmod 600 "$PAYTRAY_KEY_DIR/release-signing-key.pem"

# Derive the public key for fingerprinting and distribution to verifiers.
openssl pkey \
  -in "$PAYTRAY_KEY_DIR/release-signing-key.pem" \
  -pubout \
  -out "$PAYTRAY_KEY_DIR/release-signing-public-key.pem"

chmod 644 "$PAYTRAY_KEY_DIR/release-signing-public-key.pem"

# Record only the public-key fingerprint. Never hash or print the private key contents.
sha256sum "$PAYTRAY_KEY_DIR/release-signing-public-key.pem" \
  | tee "$PAYTRAY_KEY_DIR/release-signing-public-key.sha256"

# Confirm permissions and key type without printing private key material.
stat -c '%A %a %n' \
  "$PAYTRAY_KEY_DIR/release-signing-key.pem" \
  "$PAYTRAY_KEY_DIR/release-signing-public-key.pem"
openssl pkey -pubin \
  -in "$PAYTRAY_KEY_DIR/release-signing-public-key.pem" \
  -text -noout
```

Expected private-key permission is `600` and expected public-key permission is `644` or stricter. The public-key fingerprint must be recorded in the release evidence and independently confirmed by the security reviewer.

## 3. Environment configuration template

Do not commit a populated `.env` file. Store the private key in the approved secret manager under the exact secret name `RELEASE_SIGNING_KEY_PEM`. A protected release runner may load it for one command as follows:

```bash
set -eu
umask 077

export PAYTRAY_KEY_DIR="${PAYTRAY_KEY_DIR:-$HOME/.config/paytray/release}"

# The command substitution reads the protected file into the child process environment.
# It does not put the key into the repository or into the signed payload.
env \
  RELEASE_SIGNING_KEY_PEM="$(<"$PAYTRAY_KEY_DIR/release-signing-key.pem")" \
  RELEASE_SIGNING_PUBLIC_KEY_SHA256="$(cut -d' ' -f1 "$PAYTRAY_KEY_DIR/release-signing-public-key.sha256")" \
  RELEASE_SIGNING_PUBLIC_KEY_FINGERPRINT_VERIFIED=true \
  RELEASE_GIT_COMMIT="$(git rev-parse HEAD)" \
  RELEASE_DIRTY="false" \
  RELEASE_APPROVAL_STATUS="approved" \
  RELEASE_APPROVAL_ELIGIBLE="true" \
  RAILWAY_SETTINGS_STATUS="matched" \
  MIGRATION_EVIDENCE_STATUS="passed" \
  RECOVERY_EVIDENCE_STATUS="verified" \
  npm run backend:release:payload:check
```

The values `approved`, `true`, `matched`, `passed`, and `verified` must only be set after the corresponding real evidence exists. They are not defaults and must not be used to bypass a failed check.

A non-secret configuration template for an approved release runner is:

```dotenv
# Never place the private key value in this file.
RELEASE_SIGNING_KEY_PEM=<injected-by-approved-secret-manager>
RELEASE_SIGNING_PUBLIC_KEY_SHA256=<sha256-of-public-key-pem>
RELEASE_SIGNING_PUBLIC_KEY_FINGERPRINT_VERIFIED=<independently-confirmed-by-security-reviewer>
RELEASE_SIGNING_PUBLIC_KEY_PEM=<approved-public-key-pem-or-protected-file-injection>
RELEASE_SIGNING_KEY_SOURCE=approved-secret-manager
RELEASE_SIGNING_KEY_VERSION=<immutable-secret-version>
RELEASE_SIGNING_KEY_PROTECTED=true
RELEASE_SIGNING_FINGERPRINT_ATTESTATION_FILE=<protected-security-attestation-json>
RELEASE_GIT_COMMIT=<exact-reviewed-git-commit>

RELEASE_DIRTY=false
RELEASE_APPROVAL_STATUS=approved
RELEASE_APPROVAL_ELIGIBLE=true
RAILWAY_SETTINGS_STATUS=matched
MIGRATION_EVIDENCE_STATUS=passed
RECOVERY_EVIDENCE_STATUS=verified
```

The key must not be added to `package.json`, `.env.example`, GitHub Actions logs, Railway build logs, the release payload JSON, or any documentation artifact. The signed payload contains the public key, signature, canonical evidence, and safety flags, but never the private key.

## 4. Protected CI or Railway configuration

Configure `RELEASE_SIGNING_KEY_PEM` as a masked, write-only secret in the approved release environment. Do not use a build-time echo, command-line literal, or unmasked variable. The release environment must also provide evidence-specific values from the actual gates. A safe conceptual configuration is:

```yaml
releaseEnvironment:
  RELEASE_SIGNING_KEY_PEM:
    source: approved-secret-manager
    secret: true
    masked: true
    rotation: operator-controlled
  RELEASE_GIT_COMMIT:
    source: immutable-release-commit
  RELEASE_DIRTY:
    value: "false"
  RELEASE_APPROVAL_STATUS:
    source: completed-human-approval-artifact
  RELEASE_APPROVAL_ELIGIBLE:
    source: completed-human-approval-artifact
  RAILWAY_SETTINGS_STATUS:
    source: authenticated-redacted-settings-comparison
  MIGRATION_EVIDENCE_STATUS:
    source: migration-and-restore-artifacts
  RECOVERY_EVIDENCE_STATUS:
    source: isolated-restore-artifact
```

The release runner should be ephemeral, should not persist the private key after the command, and should restrict access to the release operator and security-approved automation. After signing, remove any temporary key material from the runner and preserve only the public-key fingerprint and signed release artifact.

## 5. Four mandatory reviewer sign-offs

The final checklist requires four distinct roles. One person may hold multiple roles only if the organization’s separation-of-duties policy explicitly allows it and the overlap is recorded. Every row requires one of the four distinct roles (`release_operator`, `protocol_finance`, `ai_data`, or `security`), a real reviewer identity, an approval decision, an ISO-8601 timestamp, and notes that identify the evidence reviewed. The release-evidence aggregator will not treat four generic approvals or duplicate roles as complete.

| Role | Mandatory responsibility | Minimum evidence reviewed | Approval condition |
|---|---|---|---|
| Release operator | Confirms the candidate commit, clean worktree, deployment target, rollback path, smoke test, and release artifact composition. | Ready manifest, deployment preflight, matched Railway settings, smoke-test record, rollback target, payload verification. | All operational checks pass and rollback is understood and acknowledged. |
| Protocol/finance reviewer | Confirms chain authority, Sablier Flow v3 configuration, token registry, decimals, finality, verifier freshness, ledger projection, and reconciliation. | Base Sepolia policy, contract/token evidence, fresh cursor, verifier audit, migration/restore evidence, reconciliation report. | No unresolved financial-integrity issue; chain evidence remains the economic authority. |
| AI/data reviewer | Confirms shadow-quality evaluation, outcome lineage, provenance, privacy boundaries, human review, and rollback target. | Baseline comparison, sample/confidence evidence, segment review, reviewer queue, provenance/retention/cost/latency evidence. | AI remains `shadow_only`; no candidate or collaboration model is promoted automatically. |
| Security reviewer | Confirms authentication, operator scope, webhook SSRF/DNS controls, secret handling, rate limits, audit logging, key custody, and incident rollback. | Security test output, webhook evidence, secret scan, public-key fingerprint, key-custody record, audit-log review. | No unresolved critical security or secret-exposure issue remains. |

## 6. Reviewer evidence form

Copy this form once for each reviewer. The placeholders must be replaced by the authorized reviewer; they are not valid approval evidence by themselves.

```yaml
review:
  role: "<release_operator|protocol_finance|ai_data|security>"
  reviewerId: "<real corporate identity, wallet, or approved reviewer ID>"
  decision: "<approved|rejected|approved_with_conditions>"
  approved: false
  approvedAt: "<real ISO-8601 timestamp with timezone>"
  scope: "production_release"
  rollbackAcknowledged: false
  releaseCommit: "<exact immutable Git commit>"
  releaseArtifactSha256: "<sha256 of signed release payload or approved artifact>"
  publicKeyFingerprintSha256: "<sha256 of public-key PEM>"
  evidenceReviewed:
    - "<artifact path, command output, dashboard link, or ticket ID>"
  findings: []
  conditions: []
  rollbackTarget: "<immutable prior release commit or approved rollback artifact>"
  notes: "<specific rationale and residual risk statement>"
  reviewerSignatureOrAttestation: "<approved organizational attestation reference>"
```

For the release approval gate to become eligible, the final human approval artifact must contain the following minimum values:

```json
{
  "approved": true,
  "reviewerId": "<real authorized reviewer identity>",
  "approvedAt": "<real ISO-8601 timestamp>",
  "scope": "production_release",
  "rollbackAcknowledged": true
}
```

The strings in angle brackets are schema placeholders only. They must never be submitted as if they were real evidence.

## 7. Sign-off acceptance checklist

### Release operator

- [ ] Exact release commit is recorded and matches the ready manifest.
- [ ] Worktree is clean and artifact hashes are captured.
- [ ] Railway settings are authenticated, redacted, and matched.
- [ ] Target is Base Sepolia (`84532`) unless separate mainnet approval exists.
- [ ] No-live-funds smoke test passed.
- [ ] Rollback target is immutable, reachable, and tested or otherwise evidenced.
- [ ] Release payload verification returned `status: verified`.
- [ ] `approved: true`, real reviewer identity, timestamp, production scope, and rollback acknowledgement are recorded.

### Protocol/finance reviewer

- [ ] Sablier Flow v3 contract and supported token registry match the target chain.
- [ ] Token decimals and participant rules are explicit and consistent.
- [ ] Verifier RPC and bounded polling are configured.
- [ ] Durable verifier cursor classification is `fresh`.
- [ ] Chain-event audit evidence is present and verifier-owned.
- [ ] Migrations through 013 passed.
- [ ] Isolated database restore was completed and independently verified.
- [ ] Reconciliation status is `ok` with no unresolved projection-lag or ledger-linkage issue.

### AI/data reviewer

- [ ] Candidate ranking remains `shadow_only`.
- [ ] Baseline comparison, sample size, confidence bound, and segment evidence are present.
- [ ] Rollback target is defined for every evaluated candidate.
- [ ] Every pending shadow run has a reviewer identity, decision, notes, and rollback context.
- [ ] Collaboration-AI provenance and retention evidence is present.
- [ ] Latency and cost bounds are evidenced.
- [ ] Raw-content exclusion and human override are tested.
- [ ] No AI output can mutate payment, ledger, outcome, reputation, or settlement state.

### Security reviewer

- [ ] Wallet challenge and session authorization tests pass.
- [ ] Operator scopes and administrative endpoints are reviewed.
- [ ] Webhook URLs reject internal/metadata targets and are revalidated at delivery.
- [ ] Webhook signatures, bounded retry, and dead-letter handling are evidenced.
- [ ] Secret scan is clean; private key is absent from repository and artifacts.
- [ ] Release key is stored in the approved secret manager with restricted access.
- [ ] Public-key fingerprint is independently verified.
- [ ] Rate limits, audit logging, and incident rollback controls are reviewed.

## 8. Final verification command sequence

Run only after the actual evidence is complete and the protected key is injected:

```bash
set -eu
cd /path/to/PAYTRAY

# Confirm the exact reviewed source and clean tree.
git rev-parse HEAD
git status --short

git diff --check

# Automated validation.
npm run test
npm run lint
DATABASE_URL="$DATABASE_URL" npm run backend:migrations:check

# Verify custody, public-key derivation, and independent security fingerprint attestation.
npm run backend:release:key:custody:check

# Release evidence gates.
DATABASE_URL="$DATABASE_URL" npm run backend:release:approval:check
npm run backend:release:manifest:check
npm run backend:deployment:check
npm run backend:railway:trial:check

# Build and inspect the signed payload using the protected secret injection above.
env RELEASE_SIGNING_KEY_PEM="$(<"$PAYTRAY_KEY_DIR/release-signing-key.pem")" \
  RELEASE_GIT_COMMIT="$(git rev-parse HEAD)" \
  RELEASE_DIRTY=false \
  RELEASE_APPROVAL_STATUS=approved \
  RELEASE_APPROVAL_ELIGIBLE=true \
  RAILWAY_SETTINGS_STATUS=matched \
  MIGRATION_EVIDENCE_STATUS=passed \
  RECOVERY_EVIDENCE_STATUS=verified \
  npm run backend:release:payload:check

# Verify the detached artifact. Replace the path with the protected artifact path.
npm run backend:release:payload:verify /protected/path/signed-release-payload.json
```

The expected final state is: key custody `status: verified`; release approval `status: ready`, `eligible: true`; manifest `status: ready`; Railway settings `matched`; recovery `verified`; payload `status: ready` with a non-null signature; detached verification `status: verified` and exit code `0`; and all four reviewer records approved with real identities and timestamps. A missing secret, mismatched derived public key, mismatched fingerprint, missing security attestation, or placeholder key version must remain blocked.

## 9. Release-blocker stop conditions

Stop and return to remediation if Railway settings are unavailable, the verifier cursor is stale or missing, recovery remains `schema_catalog_only`, reconciliation reports any unresolved financial issue, any shadow review remains pending, any reviewer rejects the release, the private key appears in logs or Git, the public-key fingerprint does not match the operator record, or any artifact reports a mutation authority. The safe result in every such case is a blocked release with no deployment or settlement mutation.
